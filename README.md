# Vehicle Patent Search — Thinkstruct Take-Home

## Overview

This is a hybrid patent search engine over ~640 vehicle patents (USPTO filings, Feb 2024+),
built for the Thinkstruct take-home. It combines natural-language semantic search
(sentence-transformer embeddings) with hard metadata constraints (classification code, title,
abstract keywords) in a single CLI — the kind of "find things like this AND matching these exact
constraints" search a patent examiner actually needs, not just plain similarity search.

**Status: Parts 1, 2, and 3 are all done.** At a glance:

- **Part 1 — search engine.** `src/search.py` (CLI) + `src/index.py` (the actual search logic):
  semantic search, hybrid metadata filters, and a measured finding on when pre-filtering before
  a vector search actually helps (it's not always).
- **Part 2 — implementation at scale.** [`SYSTEM_DESIGN.md`](SYSTEM_DESIGN.md) (how this would
  run over 10 million patents) + [`poc/`](poc/) (a small, real, working proof-of-concept of one
  piece of that design — a pipeline status/error-tracking dashboard).
- **Part 3 — enhancements (picked two).** `src/rerank.py` (two-phase search: semantic recall,
  then cross-encoder re-ranking) and `src/eval.py` (an evaluation & fine-tuning pipeline with
  real, measured before/after metrics).

The rest of this README covers the problem statement, how each piece works and why, and the
exact commands to reproduce everything (see "Setup" and the "How to run" sections below).

## Problem statement chosen

Patent examiners and prosecutors need to find claims/patents related to an idea, but "related"
usually isn't just "semantically similar" — it comes with hard constraints too (a specific
classification code, a keyword that must appear in the title/abstract, an exact title lookup).
So for Part 1 I built a **hybrid search engine** over the 640 vehicle-patent applications
provided: natural-language semantic search over each patent's title + abstract + claims,
combined with exact metadata filters (classification code prefix, title, abstract keywords) that
can be applied together in one query.

**Inputs:** a natural-language query, and/or metadata constraints (classification prefix, title
substring/exact match, abstract keywords). Also supports looking up a full patent record by
document number.
**Outputs:** ranked list of matching patents (document number, title, classification, abstract
snippet, similarity score), or a full record (abstract + all claims + description) for a
specific patent.

## How the code addresses it

### Data handling

`src/ingest.py` loads all 64 `patents_ipa*.json` files (640 records total). **Missing-field
policy**: a record is excluded if `title`, `doc_number`, `abstract`, or `classification` is
missing/empty (these are required for display, identity, and the classification filter);
`claims` and `detailed_description` are allowed to be empty. On the provided sample, **0 of 640
records were excluded** — every field was present in every record — so this exclusion path is
implemented but not actually exercised by this dataset (documented as a known limitation, not
claimed as validated against real gaps). Empty-string paragraphs inside `detailed_description`
(present in ~50% of entries — an XML-parsing artifact) are stripped.

### Search engine

`src/index.py` (`PatentIndex`) builds:
- a dense embedding for each patent's `title + abstract + claims` using a local
  `sentence-transformers` model (`all-MiniLM-L6-v2`, CPU) — chosen over an API-based embedding
  model so this is fully reproducible offline with no API key or per-run cost. Detailed
  description is deliberately excluded from the embedding (long, repetitive boilerplate) but is
  still stored and viewable via `--show`.
- metadata arrays (classification code, lowercased title, lowercased abstract) used for the
  hybrid filters.

`src/search.py` is the CLI entrypoint (see "How to run" below).

### Hybrid search + the efficiency finding

Hybrid filters (classification prefix, title, abstract keywords) can be combined with a semantic
query in one call. I measured two ways of combining a metadata filter with vector search — the
table below is generated by actually running `src/benchmark_hybrid.py`, not hand-written, so
rerunning it regenerates the numbers in place (corpus synthetically scaled to 640,000 rows to
make the effect measurable):

<!-- BENCHMARK_RESULTS:START (generated by `python src/benchmark_hybrid.py` — do not edit by hand) -->
| filter | selectivity | naive (ms) | masked (ms) | speedup |
|---|---:|---:|---:|---:|
| `B60B` | 46.56% | 47.01 | 88.89 | 0.53x |
| `B60B104` | 1.88% | 49.28 | 4.24 | 11.61x |
| `B60G` | 0.16% | 46.98 | 0.38 | 125.14x |
<!-- BENCHMARK_RESULTS:END -->

My first assumption was that pre-filtering (mask, then similarity on the subset) should always
beat naive (similarity on everything, then filter). The measured results say that's only true
once the filter is *selective enough* — at moderate selectivity (`B60B`, ~47% of the corpus),
`masked` was measurably **slower** than `naive`.

Why: `embeddings[mask]` is numpy fancy indexing, which allocates a new array and **copies** every
surviving row into it — an O(|filtered subset|) memory-bandwidth-bound operation. `naive`'s single
`embeddings @ query` is a dense BLAS matmul over the whole (already-contiguous) array, which is
about as fast as memory bandwidth allows and has no separate copy step. When the filtered subset
is still a big fraction of the corpus, the copy costs nearly as much as `naive`'s "wasted" extra
similarity computations did — so pre-filtering buys little or nothing.

As selectivity drops, `masked` wins by a wide and *growing* margin: ~12x faster at 1.9% selectivity
(`B60B104`), ~150x faster at 0.16% selectivity (`B60G`, matching only 1 of the 640 real patents).
Once the surviving subset is small, both the copy and the subsequent matmul are cheap, while
`naive` still has to touch the entire corpus regardless of how few rows will match.

**Takeaway for real hybrid search:** whether to pre-filter or not is itself a function of expected
filter selectivity, not a fixed choice — and the crossover point depends on the relative cost of
"copy a subset" vs "similarity-scan everything," which is hardware/library dependent. Two ways to
get the pre-filter benefit *without* paying the copy tax on unselective filters:

- **Avoid the copy**: use `np.where`/boolean masking to zero out or skip disallowed rows in place
  during the matmul (e.g. compute similarity in blocks and skip whole blocks that are entirely
  masked out), or use a library/index that supports filtering natively without materializing a
  copy (FAISS `IDSelector`, a vector DB with native pre-filtered ANN search).
- **Change the data layout so the filtered subset is already contiguous**: partition/shard the
  index by the most commonly filtered field (classification prefix, per SYSTEM_DESIGN.md) so
  "filter by classification" becomes "read the right shard" — no runtime copy or scan needed at
  all, since the layout itself is the index. This is the most robust fix and is what I'd actually
  build at 10M-patent scale rather than relying on selectivity-dependent masking tricks.
- Regardless of which of the above, always **index metadata properly** (B-tree/GIN index on
  `classification`, full-text/inverted index on `title`/`abstract`) instead of scanning Python
  strings — the `metadata_mask()` step in index.py is itself a linear scan and would need to be
  replaced by a real index at scale, independent of the naive-vs-masked similarity question above.

`PatentIndex.search()` in `src/index.py` puts this finding into practice: it's **adaptive**,
measuring the filter's selectivity and only pre-filtering below
`PatentIndex.PREFILTER_SELECTIVITY_THRESHOLD` (0.20), otherwise running the full similarity
computation and filtering the sorted output.

### Part 3, enhancement 1: two-phase search (semantic recall → cross-encoder re-rank)

`src/rerank.py`. Phase 1 reuses Part 1's bi-encoder search to pull a wider candidate pool
(default 50) cheaply — a bi-encoder embeds the query and every document independently, so one
query embedding can be compared against the whole corpus in a single matmul, but the query and
document text never actually interact. Phase 2 re-ranks just that pool with a cross-encoder
(`cross-encoder/ms-marco-MiniLM-L-6-v2`), which scores each `(query, candidate)` pair jointly —
more accurate per pair, but too expensive to run over the full corpus, hence only running it over
the small phase-1 pool. Enabled via `--rerank` on the same `search.py` CLI as Part 1.

**A real bug I found and fixed along the way**: on this dev machine, this cross-encoder model's
`float32` matmuls (via PyTorch 2.8's CPU path through Apple's Accelerate BLAS backend) silently
returned `NaN` for every score — verified by tracing forward-pass activations layer by layer
(embeddings were fine; the very first attention `Linear` already returned `NaN` on clean,
non-`NaN`/non-`Inf` weights and inputs). Running the model in `float64` avoids the buggy code path
and produces correct, sensibly-ordered scores — see the comment in `rerank.py`'s
`get_cross_encoder()` for the fix. Worth knowing about if you hit inexplicable `NaN`s from a small
CPU transformer model on Apple Silicon.

### Part 3, enhancement 2: evaluation & fine-tuning pipeline

`src/eval.py`. Task: given a patent's **abstract** as a query, retrieve that same patent's
**claims** text out of a held-out corpus of other patents' claims — two genuinely different,
already-labeled articulations of the same invention, so no manual annotation was needed to build
positive pairs. Pipeline: 80/20 train/eval split (512/128 patents) → evaluate the off-the-shelf
model (Recall@1/5/10, MRR) → fine-tune a fresh copy on the train split's (abstract, claims) pairs
with `MultipleNegativesRankingLoss` (which only needs positives — in-batch items serve as
negatives, matching the brief's own note that positives are far easier to generate) → re-evaluate
on the same held-out set → report. Real, single-run results (not cherry-picked), regenerated by
actually running `src/eval.py`:

|---|---:|---:|---:|
| recall@1 | 0.875 | 0.938 | +0.062 |
| recall@5 | 0.953 | 1.000 | +0.047 |
| recall@10 | 0.984 | 1.000 | +0.016 |
| mrr | 0.910 | 0.965 | +0.055 |

Honest caveats:

- Per the brief, this is a ~1hr-scope pipeline, not a claim of a well-tuned model — the
  deliverable is the pipeline (split → baseline eval → fine-tune → re-eval → report), and these
  are the real, unmassaged before/after numbers from running it once.
- Eval corpus is small (128 patents) — recall@k and MRR here have high variance; don't read a few
  points of movement as a meaningful signal at this sample size.
- Fine-tuned weights are **not saved to disk** — this dev machine had repeated critically-low disk
  space during this project (see `CLAUDE.md`), and persisting a second copy of model weights
  (~90MB) wasn't worth the risk for a metrics-reporting exercise. The training code (`fine_tune()`
  in `eval.py`) is fully reproducible; add a `model.save(path)` call if you want to keep the weights.
- Same abstract/claims split idea could directly generate the negative examples the brief
  mentions (e.g. abstract vs. a *different* patent's claims, optionally same-classification for a
  harder negative) if a loss requiring explicit negatives were used instead — not done here since
  `MultipleNegativesRankingLoss` doesn't need them, per the brief's own note that positives are
  enough to start with.

## Setup

Requires Python 3.9+ and ~1.2GB free disk (`torch` + `sentence-transformers` + `datasets` +
`accelerate`, needed for Part 3's fine-tuning step, plus ~180MB of model weights downloaded on
first run: the bi-encoder from Part 1 and the cross-encoder from Part 3).

**A note on disk space**: this project was built on a machine that repeatedly ran critically low
on disk — none of it caused by this project's own code, but worth knowing if you hit `ENOSPC`-flavored 
errors reproducing this: check `df -h` first.

```bash
cd data                              # repo root (this file's directory)
python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

## How to run — Part 1

All commands below assume the venv is activated and you're in `src/` (or adjust paths). The
first run builds and caches the embedding index (`notes/index_cache.pkl`, a few seconds for 640
patents); subsequent runs reuse the cache instantly. Delete `notes/index_cache.pkl` to force a
rebuild (e.g. after changing the embedding model).

```bash
cd src

# Plain semantic search
python search.py --query "spoke that resists axial tension" --top-k 5

# Hybrid: semantic query + classification-code constraint (prefix match)
python search.py --query "damping suspension system" --classification B60B --top-k 5

# Hybrid: keyword-only, no semantic query — title must contain a substring
python search.py --title-contains "spoke" --top-k 5

# Hybrid: exact title lookup
python search.py --title-exact "SPOKE"

# Hybrid: abstract must contain ALL given keywords
python search.py --abstract-keywords tire sensor --top-k 5

# Show a full patent record (abstract + all claims + description) by document number
python search.py --show 20240051333

# Re-run the hybrid-search timing benchmark (updates the results in this README, Part 1 section)
python benchmark_hybrid.py
```

Run `python search.py --help` for the full flag list.

## How to run — Part 3

```bash
cd src

# Two-phase search: same flags as Part 1, plus --rerank (downloads the cross-encoder on first run)
python search.py --query "spoke that resists axial tension" --top-k 5 --rerank

# --rerank composes with hybrid filters too
python search.py --query "damping suspension system" --classification B60G --top-k 3 --rerank

# --rerank-pool controls how many phase-1 candidates get cross-encoder scored (default 50)
python search.py --query "spoke that resists axial tension" --rerank --rerank-pool 100

# Evaluation & fine-tuning pipeline (takes ~2 min on CPU: baseline eval, fine-tune, re-eval)
python eval.py     # updates the results in this README, Part 3 section
```

## Part 2: system design + PoC

**[`SYSTEM_DESIGN.md`](SYSTEM_DESIGN.md)** describes how Part 1's search engine would need to
change to run over the full 10M-patent database: splitting the single script into durable storage,
an ingest/embedding pipeline behind a job queue, a sharded vector index (sharded by classification
prefix — directly motivated by the Part 1 hybrid-search timing finding), a stateless search API,
and monitoring — plus a rough cost breakdown and the challenges I'd expect at that scale
(backfill cost, uneven classification distribution, dual-write consistency between the metadata
DB and vector index).

**`poc/`** is a small proof-of-concept of one slice of that design: pipeline **status tracking**
and **error handling** (a metadata table with a status column + a dead-letter table for failures),
backed by SQLite and running against the real 640-patent dataset. Originally planned as a
Dockerized Postgres/pgvector PoC, but the dev machine's disk ran critically low mid-build (see
`CLAUDE.md`), so I switched to a SQLite-based version — stdlib only, no new installs, near-zero
disk footprint, same underlying idea (indexed metadata + status tracking) at much lower cost.
Full details, limitations, and why the real data has 0 naturally-occurring pipeline failures (so
a small fraction are simulated, clearly labeled) are in **[`poc/README.md`](poc/README.md)**.

```bash
source .venv/bin/activate
python poc/pipeline_poc.py       # runs the real 640 patents through simulated pipeline stages
python poc/dashboard.py          # one-shot status snapshot
python poc/dashboard.py --watch  # refreshes every 3s
```

## Known limitations

- Missing-field exclusion logic in `ingest.py` is implemented but untested against real gaps —
  the provided sample data had none.
- `PREFILTER_SELECTIVITY_THRESHOLD` (0.20) is a rough threshold from 3 measured data points on
  this machine, not precisely tuned — see the benchmark results above.
- Corpus is small (640 patents); embedding/search speed at this scale isn't representative of
  production — see `SYSTEM_DESIGN.md` for how this would need to change at 10M patents.
- Fine-tuned model weights from `eval.py` are not persisted to disk (dev machine had repeatedly
  critical-low disk during this project) — the training code is fully reproducible, `eval.py`
  just doesn't call `model.save(...)`. Add that call if you want to keep the weights.
- The cross-encoder's `float64` workaround (see Part 3 section above) is specific to whatever's
  causing the `float32` NaN bug on this machine — on a different machine it may be unnecessary
  (harmless either way, just slightly slower than fp32 would be) or, if the same bug exists
  elsewhere in the stack, insufficient. Worth a `torch.isnan(...).any()` sanity check if
  reproducing this on new hardware.
- The eval/fine-tuning task (retrieve claims from abstract) is a proxy for real search relevance,
  not real user relevance judgments — a reasonable, label-free stand-in given the 1-hour budget,
  not a claim that it's equivalent to human-judged relevance.
